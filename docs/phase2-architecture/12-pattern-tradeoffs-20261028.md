# Được gì, mất gì: 18 pattern kiến trúc Pha 2 (28/10/2026)

Bảng này tổng hợp đánh giá sau khi đo đối chứng kiến trúc M/H: ứng dụng đã qua nhiều vòng cải thiện, **mỗi pattern có lý do hợp lý nào để giữ lại, dù kém hiệu năng?** Tài liệu tổng hợp từ đợt rà soát mã nguồn và kiến trúc ngày 28/10/2026 ([STATUS.md](../../phase2-plan/STATUS.md)). Mọi thay đổi hành vi đều phải thông qua ADR chính thức.

## Đọc con số bridge cho đúng

Đo trên Kaggle (4 vCPU, `bridge-m-h-kaggle-v1`): monolith M `48d01c3` so với H `e0e8937` ([báo cáo bridge](../../phase2-plan/bridge/README-20261028.md)).

| Chỉ số                 | H/M                |
| ---------------------- | ------------------ |
| p95 toàn bộ            | 4,96               |
| CPU server mỗi request | 4,40               |
| RAM server             | 5,06               |
| Throughput thành công  | 0,97 (closed-loop) |

**Lưu ý trước khi quy tội:** 4,96× gộp cả việc tách service lẫn mọi tính năng thêm sau M: ma trận quyền, `currentAccount`, trigger P10/AQ-10, audit, DTO giàu hơn. Không nên quy hết cho việc tách. Máy chưa bão hòa (H dùng trung bình 2,3 lõi, tối đa 3,0 trên 4 lõi), nhưng Core chạy khoảng 0,88 lõi: Node một luồng gần bận kín nên request phải xếp hàng.

Đo lại trên VM FPT (`bridge-m-h-vm-v1`, 7 vCPU cho server, 100 user closed-loop, một lượt, chi tiết ở [báo cáo bridge](../../phase2-plan/bridge/README-20261028.md), mục "Kết quả VM"):

| Chỉ số                   | H0/M        | H1/H0        | H2/H1       |
| ------------------------ | ----------- | ------------ | ----------- |
| p95 toàn bộ              | 2,78        | 0,868        | 0,980       |
| CPU mỗi request          | 4,72        | 0,884        | 1,027       |
| RAM server               | 3,30        | 0,988        | 1,138       |
| Throughput               | 0,99        | 1,003        | 1,005       |
| Đọc theo luật chốt trước | H0 chậm hơn | H1 nhanh hơn | tương đương |

H1 = `2841d1b` gồm B+D, gỡ CQRS và migration A; H2 = H1 với Core 2 instance. **Không so 2,78 với 4,96**: VM có thêm chặng nginx `core_internal`, route notifications đã sửa, CPU khác và số vCPU khác. H1/H0 là hiệu quả gộp, không tách riêng được từng thay đổi. H2/H1 đo ở lúc máy mới dùng khoảng 8–9% CPU, nên không nói được gì về Core 2 instance khi bão hòa. Các thay đổi sau `2841d1b` (limiter in-memory, gom code, mã lỗi) **chưa được đo**.

## Ý để trình bày với thầy

- Việc tách có một khoản "thuế" và đã đo được: ở lượt VM, H0 so với M là p95 2,78×, CPU mỗi request 4,72×.
- Thuế dồn vào lời gọi đồng bộ Clinic→Core và CPU của Core. Tối ưu đã giảm p95 khoảng 13%, không xóa được khoảng cách.
- Đổi latency lấy độ tin cậy (P03), đổi CPU lấy toàn vẹn dữ liệu (trigger, revision).
- CQRS đã đo, thấy chậm, nên gỡ: quyết định theo dữ liệu.
- Claim Check là cải tiến có lời rõ ràng.
- Giữ kiến trúc tách có lý do và có điều kiện quay lại, không vì đã lỡ làm ([ADR-P14](../../phase2-plan/architecture-work/adr-p14-keep-service-split.md)).

## Việc theo sau bảng

- **Đã làm:** B+D (dòng 4, `0abe74f`); gỡ CQRS (dòng 10, `be2267b`); gỡ code chết (`31a7429`); limiter in-memory cho GET (dòng 9, `049b8a5`).
- **Đã đo:** Core 2 instance ở lượt VM: H2/H1 p95 0,980, CPU mỗi request 1,027, không có lợi ở tải vừa, tốn thêm khoảng 300 MB RAM. Chưa đo khi bão hòa.
- **Đã hoãn:** dòng 3, Clinic dùng event thu hồi phiên ([ADR-P13](../../phase2-plan/architecture-work/adr-p13-local-read-authorization.md)).
- **Đề xuất chưa quyết:** dòng 2 (gateway).
- **Không làm:** bỏ `authorize` hẳn (mất kiểm thu hồi phiên khi trang rỗng); cache có TTL kèm event invalidation (đổi ngữ nghĩa, trái ADR-05, cần ADR mới); gộp domain/validation giữa Clinic và Core (phần giống hệt như token, URL, relay đã gom vào packages ở `0f169d0`); xóa stack appointment/medical cũ của Core (đã cô lập ở commit `691b526`).
- **Chưa đo:** các thay đổi sau `2841d1b`. Cần lượt đo mới nếu muốn có số của code hiện tại.
